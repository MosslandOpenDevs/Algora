# 요청: 192.168.1.65의 `OLLAMA_NUM_PARALLEL` 상향

**수신:** Ollama 호스트 `192.168.1.65:11434` 관리자
**발신:** Algora, MOSS.AO(agentic-orchestrator) 공동
**날짜:** 2026-08-06
**요청:** `OLLAMA_NUM_PARALLEL=2` 설정 (`OLLAMA_MAX_LOADED_MODELS`는 그대로)

---

## 요약

두 서비스가 이 호스트를 공유합니다. 저희 쪽에서 고칠 수 있는 것은 이미 모두
고쳤습니다 — 이제 양쪽이 동일한 모델과 동일한 컨텍스트 크기를 요청하므로
호스트는 `gemma3:4b` 러너 하나만 유지하며 호출 사이에 재로드하지 않습니다.

남은 것은 어느 쪽도 소유하지 않은 설정입니다. **러너 하나는 한 번에 요청
하나**만 처리하는데 두 서비스가 같은 `gemma3:4b`를 쓰므로, 두 워크로드가
서로 뒤에 줄을 섭니다. 긴 생성 도중 도착한 짧은 호출은 그 생성이 끝날 때까지
대기합니다.

`OLLAMA_NUM_PARALLEL`을 2로 올리면 해결되며, 비용을 실측했습니다: **0.01 GB**
입니다.

> **범위 주의.** 이것은 러너 단위 제한이지 호스트 전체 제한이 아닙니다.
> 서로 다른 모델은 이미 나란히 로드되어 병렬로 실행됩니다 — 실측: 17.3초짜리
> `gemma3:4b` 생성의 8초 지점에 넣은 `gemma3:1b` 호출이 **0.59초**에
> 반환됐습니다. 문제는 같은 모델을 공유하는 요청들 사이에서만 발생합니다.

서버 자체 시작 설정(`server.log`, 2026-08-04 기동분, 현재 유효)으로 확인:

```
OLLAMA_NUM_PARALLEL:1            <-- 이 요청의 대상
OLLAMA_MAX_LOADED_MODELS:0       <-- 0 = 자동. 이미 적절하므로 그대로 두십시오
OLLAMA_MAX_QUEUE:512
OLLAMA_KEEP_ALIVE:5m0s           <-- 저희 호출별 keep_alive가 우선 적용됨
OLLAMA_FLASH_ATTENTION:false
OLLAMA_KV_CACHE_TYPE:            <-- 비어 있음 = f16
OLLAMA_VULKAN:true
```

## 이미 조치한 것

| | 이전 | 현재 |
|---|---|---|
| Algora `num_ctx` | 8192 | **16384** |
| MOSS.AO `num_ctx` | 16384, 단 한 경로에 4096 오버라이드 | 전 경로 **16384** |
| 모델 | 양쪽 `gemma3:4b` | 동일 |

같은 모델에 대해 `num_ctx` 값이 다르면 러너가 교체되므로, 값이 어긋나면
교대할 때마다 전체 언로드/재로드가 발생했습니다. 2026-08-06에 통일했고,
이후 호스트는 연속 폴링 내내 `ctx=16384` 러너 하나를 유지했습니다.

## 남은 문제 — 실측

**공유 `gemma3:4b` 러너 내부의 직렬화**입니다. 3,000토큰 생성을 시작한 뒤,
같은 모델에 "say OK" 수준의 사소한 요청을 8초 지점에 넣었습니다:

```
긴 생성        ..................................... 16.55초에 완료
짧은 요청          t=8초에 발사 ..................... 16.6초에 반환
```

짧은 요청은 병렬로 실행되지 않고 긴 생성이 끝나기를 기다렸습니다. 다른
규모에서도 재확인했습니다(8.7초 생성의 6초 지점에 넣은 프로브가 8.8초 반환).

두 워크로드의 형태가 정반대라 이것이 문제가 됩니다:

- **Algora** — 분당 약 2회, 출력 19–31토큰, 차단되지 않으면 1초 미만.
- **MOSS.AO** — 빈도는 낮지만 수천 토큰 프롬프트와 수십 초 생성.

## 변경 비용: 0.01 GB

`OLLAMA_NUM_PARALLEL=2`는 슬롯 2개분 KV 캐시를 할당합니다. 합의된
`num_ctx=16384` 기준으로 32768 토큰 창에 해당합니다. 각 창을 실제로 로드하고
`/api/ps`의 `size_vram`을 읽어 이 호스트에서 직접 측정했습니다:

| 창 크기 | 상주 VRAM |
|---|---|
| 4096 | 2.88 GB |
| 8192 | 3.03 GB |
| 16384 | 2.89 GB |
| **32768** (= 16384 슬롯 2개) | **2.90 GB** |

`gemma3`는 대부분 레이어에서 슬라이딩 윈도우 어텐션을 쓰므로 KV 캐시가
컨텍스트 길이에 거의 비례하지 않습니다 — 사용량은 Q4_K_M 가중치가 지배합니다.
슬롯을 2배로 해도 비용은 2배가 아니라 약 10 MB입니다.

카드 기준으로는, 서버가 기동 시 직접 탐지한 값이 다음과 같습니다:

```
NVIDIA GeForce RTX 5060, discrete, CUDA 12.0, driver 13.1
total="8.0 GiB"  available="6.9 GiB"
```

현재 상주는 `gemma3:4b` 2.89 GB + `gemma3:1b` 0.88 GB로 **6.9 GiB 중 약
3.8 GiB**이며 약 3.1 GiB가 남습니다. 이번 변경이 추가하는 약 10 MB는 그
안에서 충분히 여유롭습니다.

## 요청하는 정확한 변경

Windows 호스트에서 Ollama가 실행되는 사용자 계정으로:

```powershell
setx OLLAMA_NUM_PARALLEL 2
```

이후 Ollama를 재시작합니다(트레이 아이콘에서 종료 후 재실행). 시작 시점에
값을 읽으므로 재시작이 필요합니다. 확인:

```powershell
Select-String -Path "$env:LOCALAPPDATA\Ollama\server.log" -Pattern "server config" | Select-Object -Last 1
```

의도적으로 건드리지 않는 것:

- **`OLLAMA_MAX_LOADED_MODELS`** — 현재 `0`(자동)이며 이것이 맞습니다. 서로
  다른 모델이 공존하는 현재 동작이 잘 작동하므로 변경을 원하지 않습니다.
- **`OLLAMA_KEEP_ALIVE`** — 서버 기본값 `5m`이지만 Algora가 호출마다
  `keep_alive: 15m`을 보내고 MOSS.AO도 충분히 자주 호출합니다. 서버 측 변경
  불필요.

2가 무리 없다면 3으로 두 서비스에 각 1슬롯 + 여유 1슬롯을 줄 수 있고 한계
비용도 비슷합니다. 다만 2에서 시작해 측정하는 편을 선호합니다.

**선택 사항, 이 요청과는 별개:** `OLLAMA_FLASH_ATTENTION`이 `false`이고
`OLLAMA_KV_CACHE_TYPE`이 비어 있습니다(f16). 플래시 어텐션을 켜면 보통 KV
캐시 메모리가 줄고 처리량이 개선되며, 이후 여유가 빠듯해지면 양자화 KV
캐시(`q8_0`)도 쓸 수 있습니다. 시도해 볼 만하지만 별개 변경이고 여기서
측정하지는 않았습니다.

## 검증 방법

```bash
curl -s $OLLAMA/api/ps          # gemma3:4b 1개, context_length 16384 기대
```

이후 위 인터리빙 테스트를 재실행합니다. 짧은 요청이 긴 생성을 기다리지 않고
1초 미만에 반환되어야 합니다. 효과가 없더라도 포함해 수치를 그대로
회신하겠습니다.
