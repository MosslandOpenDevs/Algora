# 요청: 192.168.1.65의 `OLLAMA_NUM_PARALLEL` 상향

**수신:** Ollama 호스트 `192.168.1.65:11434` 관리자
**발신:** Algora, MOSS.AO(agentic-orchestrator) 공동
**날짜:** 2026-08-06
**요청:** `OLLAMA_NUM_PARALLEL=2` 설정 (`OLLAMA_MAX_LOADED_MODELS`는 1로 유지)

---

## 요약

두 서비스가 이 호스트를 공유합니다. 저희 쪽에서 고칠 수 있는 것은 이미 모두
고쳤습니다 — 이제 양쪽이 동일한 모델과 동일한 컨텍스트 크기를 요청하므로
호스트는 `gemma3:4b` 인스턴스 하나만 유지하며 호출 사이에 재로드하지
않습니다.

남은 것은 어느 쪽도 소유하지 않은 설정입니다. 호스트가 **한 번에 요청 하나**만
처리하기 때문에 두 워크로드가 서로 뒤에 줄을 섭니다. 긴 생성 도중 도착한
짧은 호출은 그 생성이 끝날 때까지 대기합니다.

`OLLAMA_NUM_PARALLEL`을 2로 올리면 해결되며, 비용을 실측했습니다: **0.01 GB**
입니다.

## 이미 조치한 것

| | 이전 | 현재 |
|---|---|---|
| Algora `num_ctx` | 8192 | **16384** |
| MOSS.AO `num_ctx` | 16384, 단 한 경로에 4096 오버라이드 | 전 경로 **16384** |
| 모델 | 양쪽 `gemma3:4b` | 동일 |

`num_ctx` 값마다 별도 러너이므로, 값이 어긋나면 교대할 때마다 전체
언로드/재로드가 발생했습니다. 2026-08-06에 통일했고, 이후 호스트는 연속
폴링 내내 `ctx=16384` 인스턴스 하나를 유지하며 전환이 없었습니다.

## 남은 문제 — 실측

직렬화입니다. 3,000토큰 생성을 시작한 뒤, 8초 지점에 "say OK" 수준의 사소한
요청을 넣었습니다:

```
긴 생성        ..................................... 16.55초에 완료
짧은 요청          t=8초에 발사 ..................... 16.6초에 반환
```

짧은 요청은 병렬로 실행되지 않고 긴 생성이 끝나기를 기다렸습니다. 다른
규모에서도 재확인했습니다(8.7초 생성의 6초 지점에 넣은 프로브가 8.8초 반환).

두 워크로드의 형태가 정반대라 이것이 문제가 됩니다:

- **Algora** — 분당 약 2회, 출력 19–31토큰, 차단되지 않으면 1초 미만.
- **MOSS.AO** — 빈도는 낮지만 수천 토큰 프롬프트와 수십 초 생성.

현재 MOSS.AO의 모든 생성이 그 사이에 도착하는 Algora 호출 전부를 막고,
Algora의 꾸준한 주기가 MOSS.AO의 시작 순서를 늦춥니다.

## 변경 비용: 0.01 GB

`OLLAMA_NUM_PARALLEL=2`는 슬롯 2개분 KV 캐시를 할당합니다. 합의된
`num_ctx=16384` 기준으로 32768 토큰 창에 해당합니다. 각 창을 실제로 로드하고
`/api/ps`의 `size_vram`을 읽어 이 호스트에서 직접 측정했습니다:

| 창 크기 | 상주 VRAM |
|---|---|
| 4096 | 2.88 GB |
| 8192 | 3.03 GB |
| 16384 | 2.89 GB |
| **32768** (= 16384 슬롯 2개) | **2.90 GB** |

`gemma3`는 대부분 레이어에서 슬라이딩 윈도우 어텐션을 쓰므로 KV 캐시가
컨텍스트 길이에 거의 비례하지 않습니다 — 사용량은 Q4_K_M 가중치가 지배합니다.
슬롯을 2배로 해도 비용은 2배가 아니라 약 10 MB입니다.

카드의 전체 용량은 저희가 직접 확인하지 못했습니다(이 호스트에 셸 접근이
없습니다). 저희가 근거로 삼은 값은 약 8 GB이고 상주는 약 2.9 GB입니다. 그
값이 맞다면 여유 용량은 제약이 아닙니다.

## 요청하는 정확한 변경

```
OLLAMA_NUM_PARALLEL=2
```

의도적으로 건드리지 않는 것:

- **`OLLAMA_MAX_LOADED_MODELS`** — 1로 유지해 주십시오. 저희가 원하는 것은
  공유 인스턴스 하나이며, 두 번째 모델이 로드되는 것이 바로 저희가 하루를
  들여 제거한 스래싱의 원인이었습니다.
- **`OLLAMA_KEEP_ALIVE`** — Algora가 호출마다 `keep_alive: 15m`을 요청하고
  MOSS.AO가 충분히 자주 호출하므로 서버 측 변경은 불필요합니다.

2가 무리 없다면 3으로 두 서비스에 각 1슬롯 + 여유 1슬롯을 줄 수 있고 한계
비용도 비슷합니다. 다만 2에서 시작해 측정하는 편을 선호합니다.

## 검증 방법

```bash
curl -s $OLLAMA/api/ps          # gemma3:4b 1개, context_length 16384 기대
```

이후 위 인터리빙 테스트를 재실행합니다. 짧은 요청이 긴 생성을 기다리지 않고
1초 미만에 반환되어야 합니다. 효과가 없더라도 포함해 수치를 그대로
회신하겠습니다.

## 연락

두 팀 모두 ao 박스를 통해 연락 가능합니다(`/home/atrn/Algora`,
`/home/atrn/agentic-orchestrator`). 한산한 시간대로 재시작 일정을 잡거나,
변경 직후 저희가 즉시 검증을 돌리는 것 모두 가능합니다.
