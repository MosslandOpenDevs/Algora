# 공유 Ollama 호스트: 적용된 튜닝과 실측

**호스트:** `192.168.1.65:11434` — Windows, NVIDIA RTX 5060, Ollama 0.32.5
**공유:** Algora, MOSS.AO(agentic-orchestrator)
**상태:** 2026-08-06 전부 적용 및 검증 완료

---

## 적용된 설정

| | 값 | 소관 |
|---|---|---|
| 모델 | `gemma3:4b` | 양쪽 서비스 |
| `num_ctx` | **16384** | 양쪽 서비스 (조율 값 — 아래 참고) |
| `OLLAMA_NUM_PARALLEL` | **2** (이전 1, 기본값) | 호스트 |
| `OLLAMA_MAX_LOADED_MODELS` | **2** (이전 `0`/자동) | 호스트 |
| `OLLAMA_FLASH_ATTENTION` | **true** (이전 false) | 호스트 |
| `OLLAMA_KV_CACHE_TYPE` | **q8_0** (이전 빈 값/f16) | 호스트 |
| `OLLAMA_GPU_OVERHEAD` | **1 GiB** 예약 | 호스트 |
| `keep_alive` | 호출당 `15m` | Algora |

> `OLLAMA_NUM_PARALLEL`은 프로세스 시작 시에만 읽으므로, `setx`로 바꿔도
> Ollama를 재시작해야 반영됩니다. 환경변수가 아니라 아래 로그에서 실제
> 적용값을 확인하십시오 — 둘이 다를 수 있습니다.

## 스케줄링 모델

가정이 아니라 실측입니다. 혼동하기 쉬운 세 가지 서로 다른 동작:

| 상황 | 동작 |
|---|---|
| 같은 모델, 다른 `num_ctx` | 러너 **교체** — 전체 언로드/재로드, 4.3–4.5초 |
| 같은 러너, 동시 요청 | **슬롯 공유** (이전: `NUM_PARALLEL=1`에서 직렬화) |
| 다른 모델 | **별도 러너, 실제 병렬** |

세 번째는 직접 확인했습니다: 17.3초짜리 `gemma3:4b` 생성의 8초 지점에 넣은
`gemma3:1b` 호출이 **0.59초**에 반환됐습니다.

첫 번째가 `num_ctx`를 상한이 아니라 *조율* 값으로 만드는 이유입니다. 두
서비스 모두 단독으로는 16384가 필요 없지만(Algora의 실제 최대 프롬프트는
약 4.5k 토큰), 값이 어긋나면 교대할 때마다 재로드를 물게 됩니다. 한쪽만
바꾸면 안 됩니다.

## `NUM_PARALLEL`을 올린 이유

`NUM_PARALLEL=1`에서는 러너 하나가 한 번에 요청 하나만 처리하므로 두
서비스가 서로를 막았습니다. 16.5초 생성의 8초 지점에 넣은 사소한 호출이
16.6초에 반환됐습니다 — 그냥 기다린 것입니다.

두 워크로드의 형태가 정반대라 양방향으로 비쌌습니다:

- **Algora** — 분당 약 2회, 출력 19–31토큰, 차단되지 않으면 1초 미만.
- **MOSS.AO** — 빈도는 낮지만 수천 토큰 프롬프트, 수십 초 생성.

## 결과 — 4가 아니라 2인 이유

둘 다 라이브로, 각각 단일 요청 대조군을 앞뒤에 붙여 측정했습니다(300토큰
요청 4개 동시 발사):

| `NUM_PARALLEL` | `gemma3:4b` VRAM | 동시 4개 집계 | 순차 대비 |
|---|---|---|---|
| 1 | 2.89 GB | 약 107 tok/s | 1.0배 |
| **2** (현재) | **2.98 GB** | **173 tok/s** | **1.6배** |
| 4 | 3.30 GB | 235 tok/s | 2.2배 |

단일 요청 decode는 어느 설정에서도 변하지 않습니다(4에서 106.6 / 106.9,
2에서 106.9 tok/s. 변경 전 기준선 약 109 tok/s). 슬롯 수는 완료 시각에
그대로 드러납니다. 2에서는 동시 요청 4개가 두 쌍으로 끝나고(3.61초, 3.61초,
6.88초, 6.90초), 4에서는 넷이 함께 끝납니다.

**2를 택한 이유**는 `MAX_LOADED_MODELS`가 2이고 `NUM_PARALLEL`이 *러너마다*
적용되기 때문입니다. 4라면 상주 모델 두 개가 도합 슬롯 8개를 잡습니다. 2는
처리량 이득의 약 74%를 VRAM 비용의 약 22%로 확보하면서, 제3자 모델이 로드될
자리를 남깁니다.

이 여유는 가정이 아닙니다. ctx 4096의 `gemma3:1b`(우리 것이 아니라 LAN의
다른 클라이언트)가 이 호스트에 주기적으로 나타납니다. 둘 다 상주시킨 상태로
측정:

```
gemma3:4b  ctx=16384  2.98 GB
gemma3:1b  ctx= 4096  0.95 GB
                      ------- 가용 약 5.9 GiB 중 3.92 GB
                              (6.9 GiB 가용 - 1.0 GiB GPU_OVERHEAD)
```

여유 약 2.0 GB이고, 동시에 서빙됩니다. `gemma3:4b` 생성 2초 지점에 넣은
`gemma3:1b` 프로브가 **0.38초**에 반환됐으며 축출은 없었습니다.

> 이전 추정에 대한 참고: 슬롯 2개를 `num_ctx=32768` 단일 러너로 대용해 약
> 10 MB로 예측했는데, 이 대용값은 과소 예측합니다. 위 표의 실측값을
> 신뢰하십시오.

## 측정 주의사항 — 비싸게 배운 것

변경 도중 표본에서 decode **5.2 tok/s**, prefill 101 tok/s가 나왔고 이를
심각한 성능 저하로 읽어 그렇게 보고했습니다. 사실이 아니었습니다.
`NUM_PARALLEL > 1`이 되는 순간 Algora 자신의 라이브 프로덕션 트래픽이 GPU를
실제로 공유하므로, 대조군 없이 뽑은 "단일 요청" 표본은 사실상 *n*중 경합을
측정한 것입니다.

**이 호스트에서 동시성 측정을 할 때는 직전·직후에 단일 요청 대조군을 반드시
같이 재십시오.** 이 호스트는 결코 유휴 상태가 아니므로, 대조군 없는 수치는
의미가 없습니다.

## 플래시 어텐션 + `q8_0` KV 캐시: 실측 결과 효과 없음

여기서 유망한 선택지로 제안했고 이후 호스트에 적용됐습니다. 동일한 대조군
방식으로 재측정했습니다:

| | f16 KV, FA 없음 | FA + `q8_0` KV |
|---|---|---|
| 단일 요청 (대조군) | 106.6 / 106.9 tok/s | 104.7 / 107.2 tok/s |
| 동시 4개, 집계 | 235 tok/s | 229 tok/s |
| 상주 VRAM | 3.30 GB | 3.30 GB |

**어느 축에서도 유의미한 차이가 없습니다** — 편차는 실행 간 노이즈 범위
안이고 VRAM은 소수점 둘째 자리까지 동일합니다. 이유는 `num_ctx`가 이
호스트에서 저렴한 것과 같은 성질로 보입니다. gemma3는 대부분 레이어에서
슬라이딩 윈도우 어텐션을 쓰므로 KV 캐시가 이미 작고, 그것을 양자화해도
측정할 만한 이득이 남지 않습니다.

켜 둬도 해롭지 않지만 여유 확보 수단으로 기대하지는 마십시오. 이 호스트의
VRAM이 빠듯해지면 지렛대는 KV 캐시 형식이 아니라 모델 선택이나
`NUM_PARALLEL`입니다.

## 변경하지 않은 것

- **`OLLAMA_KEEP_ALIVE`** — 서버 기본값 `5m`이지만 Algora의 호출당 `15m`이
  우선 적용됩니다.

## 검증

```bash
curl -s http://192.168.1.65:11434/api/ps    # gemma3:4b 1개, context_length 16384
```

```powershell
Select-String -Path "$env:LOCALAPPDATA\Ollama\server.log" -Pattern "server config" | Select-Object -Last 1
Select-String -Path "$env:LOCALAPPDATA\Ollama\server.log" -Pattern "inference compute" | Select-Object -Last 1
```

두 번째 명령으로 백엔드가 설정에 함께 켜져 있는 Vulkan 경로가 아니라
CUDA(`library=CUDA`, compute 12.0, driver 13.1)인지 확인합니다. Ollama를
재시작할 때마다 확인할 가치가 있습니다 — 백엔드가 조용히 바뀌면 겉보기에는
성능 저하와 정확히 똑같아 보이기 때문입니다.
