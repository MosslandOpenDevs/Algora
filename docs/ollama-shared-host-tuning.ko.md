# 공유 Ollama 서비스: 일반화된 튜닝 참고서

이 문서는 여러 워크로드가 공유하는 GPU 기반 Ollama 서비스에서 재사용할
수 있는 튜닝 교훈을 정리합니다. 운영 엔드포인트, 호스트명, 테넌트명,
OS/GPU 식별자, 드라이버 버전, 절대 용량 수치는 의도적으로 제외했습니다.
`LOCAL_LLM_ENDPOINT`와 호스트별 설정은 버전 관리되지 않는 배포 설정에
보관하세요.

아래 값은 참고용 출발점이며 실제 프로덕션 설정을 의미하지 않습니다. 배포
환경마다 다시 측정하세요.

## 참고 기준선

| 설정                       |            참고 값 | 범위                             |
| -------------------------- | -----------------: | -------------------------------- |
| 모델                       |        `gemma3:4b` | 워크로드별                       |
| `num_ctx`                  |            `16384` | 같은 모델을 쓰는 모든 클라이언트 |
| `OLLAMA_NUM_PARALLEL`      |                `2` | 호스트                           |
| `OLLAMA_MAX_LOADED_MODELS` |                `2` | 호스트                           |
| `OLLAMA_FLASH_ATTENTION`   |             `true` | 호스트                           |
| `OLLAMA_KV_CACHE_TYPE`     |             `q8_0` | 호스트                           |
| `OLLAMA_GPU_OVERHEAD`      | 배포 환경별 예약값 | 호스트                           |
| `keep_alive`               |              `15m` | 호출별                           |

호스트 수준 환경변수는 프로세스 시작 시 읽힙니다. 변경 후 Ollama를
재시작하고, 환경변수와 실행 중인 프로세스가 같을 것이라고 가정하지 말고
서비스 로그에서 실제 값을 확인하세요.

## 스케줄링 모델

통제된 측정에서 다음 세 가지 행동을 구분했습니다.

| 상황                      | 행동                                  |
| ------------------------- | ------------------------------------- |
| 같은 모델, 다른 `num_ctx` | 러너가 교체되어 재로드 발생           |
| 같은 러너의 동시 요청     | 설정된 슬롯을 공유                    |
| 다른 모델                 | 용량이 허용하면 별도 러너로 동시 실행 |

따라서 `num_ctx`는 컨텍스트 상한이자 조율 값입니다. 같은 모델을 사용하는
클라이언트는 같은 값을 써야 하며, 그렇지 않으면 교대로 들어오는 요청이 상주
러너를 반복 교체할 수 있습니다. 가장 큰 제한된 프롬프트와 여유분을 기준으로
값을 정하고 모든 클라이언트에서 함께 변경하세요.

## `OLLAMA_NUM_PARALLEL` 선택

실제적인 프롬프트·출력 길이로 벤치마크하세요. 통제된 참고 측정의 정규화된
결과는 다음과 같습니다. 호스트를 식별할 수 있고 다른 하드웨어에 그대로 적용되지
않는 절대 처리량·메모리 값은 제외했습니다.

| `NUM_PARALLEL` | 상주 메모리 비율 | 총 처리량 비율 |
| -------------: | ---------------: | -------------: |
|              1 |            1.00x |          1.00x |
|              2 |         약 1.03x |        약 1.6x |
|              4 |         약 1.14x |        약 2.2x |

참고 환경에서는 `2`를 선택했습니다. 대부분의 처리량 향상을 얻으면서 다른
모델이 상주할 여유를 남겼기 때문입니다. 이를 출발점으로만 사용하고, 대상
호스트에서 `NUM_PARALLEL * MAX_LOADED_MODELS`가 의미하는 총 예약량을 확인하세요.

통제된 두 번째 모델 공존 테스트에서도 여유 용량이 충분하면 별도 모델 러너가
축출 없이 함께 상주하며 동시에 요청을 처리할 수 있음을 확인했습니다. 관계없는
백그라운드 트래픽을 관찰해 추론하지 말고, 통제하는 테스트 워크로드로 재현하세요.

## 측정 원칙

공유 호스트의 백그라운드 트래픽은 벤치마크를 오염시킬 수 있습니다. 동시성 테스트마다:

1. 테스트 직전에 단일 요청 대조군을 실행합니다.
2. 고정된 프롬프트와 출력 한도로 동시 워크로드를 실행합니다.
3. 직후에 같은 단일 요청 대조군을 다시 실행합니다.
4. 정규화된 지연·처리량·상주 메모리를 비교합니다.

이런 대조군이 없으면 속도 저하가 백엔드나 설정 회귀가 아니라 다른 워크로드와의
경합으로 발생한 것일 수 있습니다.

## 플래시 어텐션과 KV 캐시 포맷

참고 환경에서 플래시 어텐션과 `q8_0` KV 캐시를 활성화했지만 실행별 편차를 넘는
유의미한 변화는 없었고, 상주 메모리도 측정 정밀도 내에서 같았습니다. 활성화해도
무방하지만 보장된 용량 여유로 간주하면 안 됩니다. 모델 선택과 병렬성이 주요
제어 수단이며, 다른 아키텍처에서는 다시 측정하세요.

## Keep-alive

참고 클라이언트는 서버 기본값보다 길 수 있는 `keep_alive: 15m`을 전송합니다. 공유
서비스에서 긴 상주 시간은 간헐적인 호출 사이의 불필요한 재로드를 막을 수 있습니다.
다른 모델을 받아들여야 하는 필요와 균형을 맞추고, 호스트별 가정을 공개하지 말고
워크로드별로 설정하세요.

## 검증

실제 엔드포인트는 로컬 또는 배포 환경 파일에만 설정하고, 읽기 전용 검증에는
설정된 값을 사용하세요.

```bash
OLLAMA_BASE_URL="${LOCAL_LLM_ENDPOINT:-http://localhost:11434}"
curl -s "${OLLAMA_BASE_URL}/api/ps"
```

재시작 후 Ollama 서비스 로그에서 실제 서버 설정과 추론 백엔드를 확인하세요.
로그 경로와 가속기 세부정보는 호스트마다 다르며 비공개 운영 문서에 보관해야 합니다.
